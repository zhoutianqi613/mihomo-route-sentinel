### 1.2 v1.8.0

- **原问题：** 健康与准入混淆、扫描自扰、恢复共用预算，以及旧证据被错误用于新选择。
- **主要变化：**
  - 分开健康、准入、动作与预算；严格证据绑定实际选择与叶子。
  - 扫描全部使用per-node，共享真实在途容量；优化与恢复预算分池，增加有界rescue。
  - 四篇文档统一为连续编号的两级目录；配置字段与规则说明分离，交付路线图同步当前状态。
- **本地证据：** 算法交付233项通过；补充文档结构、原生二级标题与配置表回归后，全量244项通过。真实只读Dry Run候选峰值8/配置8，选择未改变。完整证据与退回记录见第03节。
- **投用证据：**
  1. 22:07:32启动1.8.0；Windows任务Running/HiddenHost，PID22624，守卫均ready。
  2. 22:07:40首轮100%成功、平均686ms、最大877ms；状态为healthy + usable。
  3. 22:08:09复核100%成功、平均568ms、最大671ms；准入达到strict。
- **后台观察：**
  - 22:11:00的per-node快照耗时25907ms，预算75000ms；得到4个已验证候选。
  - 发现阶段72次逻辑探测/72次请求，峰值并发8；严格复测16次请求，峰值并发4。
  - 启动至22:11:07共9条健康评估，`watchdog-cycle-failed`为0。部分延迟退化/尖峰后自行恢复，无实际切换事件。
- **限制：**
  - 已停用组级delay；后台完整验证、前台冷发现、紧急复核分别计时，不再承诺完整严格扫描3秒完成。
  - 尚未强制注入真实故障。持续观察与Git正式发布分别验收，本地测试或首轮成功不能证明长期稳定。

### 1.3 v1.7 及更早

**v1.7.1：紧急恢复修复（2026-10-26）**

- **原问题：** 约750ms窗口拒绝较慢但可响应节点；局部成功又可能过早消耗预算。
- **主要变化：** 快速一轮无结果或不完整时，追加最多3秒的一轮实时复核；保留相对改善、预算和待严格准入身份。
- **本地证据：** 提交`91a6d81`，172项测试通过。
- **投用证据：** 真实扩展恢复在4.2秒内从日本05切到香港04，当次候选100%成功。
- **后台观察：**
  - 自动恢复已触发，但多节点继续出现TLS超时并耗尽原有切换预算。
  - 六个跨地区候选两轮复核后，执行一次有日志的维护恢复至台湾02。
  - **网络响应：** 后续三轮HTTPS/WebSocket探测均有响应；401/403只证明网络可达。
  - **完整下载：** 三次官方文档下载均为HTTP 200，每次412145字节且完整成功。
  - **验收边界：** 未经鉴权的WebSocket未完成101升级，长连接未验收；后续延迟仍超过严格准入线。
- **限制：** 此次修复证明恢复控制流程可工作；后续节点仍抖动，节点池与长期连接稳定性仍缺证据。

**v1.7.0：负载可观测（2026-10-25）**

- **原问题：** 健康期全组探测频繁，状态无法解释隐含负载。
- **主要变化：** 降低快照刷新频率、受控逐节点并发、取消超时请求并增加负载统计。
- **本地证据：** 提交`541eea8`，当时157项测试通过；真实Dry Run为2536ms，正式状态未改变。
- **限制：** 以上为该版本的历史证据；其组级扫描方式已由1.8.0替换。

**v1.6.0：快速恢复**

- **原问题：** 故障后才扫描与串行复核增加等待。
- **主要变化：** 候选快照、并行有界复核、应急相对可用接管。
- **本地证据：** 提交`9858738`。
- **限制：** 一秒目标仅适用于限定恢复窗口，不能视为完整故障恢复时限。

**v1.5.0：出口一致**

- **原问题：** 嵌套自动组在验证期间继续换叶子。
- **主要变化：** 叶子可直接选择时，先固定当前叶子并重新严格准入。
- **本地证据：** 提交`73f5d04`。
- **限制：** 不对无法安全改写的合法拓扑强行扁平化。

**v1.4系列：恢复时效**

- **原问题：** 全候选扫描曾耗时约123–160秒；切前拒绝占用切换名额。
- **主要变化：** 后台3秒有界扫描、正确统计实际选择、及时清除扫描运行态。
- **本地证据：** 提交`fb071ec`、`9394779`、`61cbe8e`。
- **限制：** 扫描时限与总恢复时限分开；旧版扫描承诺不能套用于1.8.0完整严格验证。

**v1.3系列：选择质量**

- **原问题：** 健康但偏慢、间歇退化和候选被过早淘汰。
- **主要变化：** 滚动退化、周期择优、严格/临时候选与安全恢复。
- **本地证据：** 提交`d668c41`。
- **限制：** 策略演进不代表全网络条件最优。

**初始版本（未标号）：可用基线与守卫（2026-10-23）**

- **原问题：** 人工换节点、错误回滚、可见后台窗口和配置旁路。

### 3.4 退回与复验

**项目经理退回记录**

| 退回项 | 原因与影响 | 修正要求 |
|---|---|---|
| 状态模块：严格样本完整性 | 只计轮数，未校验每轮业务URL覆盖，缺样本可能被判严格通过 | 严格推导检查每轮完整URL；未知目标集合不能自行推导strict |
| 状态模块：旧回滚迁移 | 旧 `rollback-recovered / verified=true` 只保证健康线，不能据此宣称严格准入 | 排除该旧审计作为strict证据，保留待复核身份 |
| 集成算法：单次运行相对改善 | 非后台恢复绕过紧急门禁，可能从50%/300ms切到50%/700ms | 所有恢复入口均拒绝无实时相对改善候选，并留失败回归 |
| 集成算法：回滚严格证据 | 合法的一轮切后配置可能使一次300ms回滚样本被标strict | 严格证据至少两轮且业务目标完整；一轮回滚只能usable |
| 扫描调度：实际在途并发 | 真实Dry Run发现配置8但峰值9；请求超时返回后底层尚未结束，逻辑worker可能继续开启新节点请求 | 容量随真实请求结束释放，排队仍遵守截止，不能只修饰统计数字 |
| 集成预算：救援资格与恢复证据 | 初始硬故障恢复到usable后仍可能沿用最初救援资格；旧临时候选可能已失效或实际叶子已变化 | 按实际出口最新健康决定救援资格；恢复前重测，切后叶子变化时重测实际叶子，不能继承旧成功样本 |

## 04 文档维护

**文档与迭代如何保持一致**

### 4.1 内容来源

| 内容 | 唯一正文来源 / 状态来源 | 谁在什么事件更新 |
|---|---|---|
| 背景、范围、产品结论 | `PRODUCT.md` | 本次需求/产品负责人，在定位、范围或可用性变化时更新 |
| 操作与配置 | `README.md` | 本次实现者，在用户可见操作和配置变化的同一变更中更新 |
| 流程与设计取舍 | `docs/design.md` | 本次实现者，在控制流程或关键决策变化时说明原因和代价 |
| 迭代目标、阶段结果与已确认缺口 | `docs/iterations.md` | 本次需求/产品负责人，在迭代开始或验收结束时更新 |
| 执行任务状态 | 飞书Backlog | 执行者在开始、阻断、完成时更新；本页只读取快照 |

**责任边界：** Bear确认需求取舍、顺序与验收目标；接手项目的开发Agent在同一次交付中更新文档，避免要求Bear再把聊天总结抄进飞书。

### 4.2 发布流程

1. **更新源页：** 判断背景/边界、操作、策略或阶段结论是否变化，只改对应正文；没有影响时说明原因。
2. **检查与预览：** 运行`npm run docs:check`检查内容、链接、标记与CLI帮助；原有测试检查README字段覆盖。再运行`npm run docs:publish`，读取Backlog、生成四篇稿并比较源Hash与发布回执，默认不改飞书。
3. **按授权发布：** 获得本轮同步授权后运行`npm run docs:publish -- --apply`，更新变化页并读回，记录源Hash、线上revision与结果。远端手改或源稿变化时停止覆盖。
4. **核对结果：** 检查本项目文档同步日期；任何一页失败即报告未全部发布。没有飞书登录时保留源稿与预览，授权恢复后重试。

**工具范围：** 仅处理固定四篇飞书文档与本项目文档同步日期；不会重启Sentinel、探测代理、修改节点、提交或推送Git。

**恢复资料：** 生成稿、回执与上一版正文保存在已忽略的`var/docs-publish/`；凭据由lark-cli管理。

> [!WARNING]
> **发布限制：** 需要Node.js、lark-cli与有效用户授权。更换工作目录或丢失回执时，先人工核对线上正文并恢复发布基线；工具遇到此情形会停止。

**版本边界：** 源文档仍需按正常Git流程提交，本地草稿不能当作GitHub已发布版本。本轮未自动提交或推送。

**运行方式：** 事件触发、单向生成、按变化发布。当前未配置定时任务或GitHub Actions；先验证维护效果，再决定是否接入每次发布流程。

### 4.3 审查范围

公开实践提供的是取舍依据，不是证明本项目已经长期维护成功：

- **按问题分工：** [Diátaxis](https://diataxis.fr/application/)区分学习、操作、参考和解释。本项目采纳读者问题导向，操作与配置参考仍集中在README。
- **保留决策理由：** [arc42架构决策](https://docs.arc42.org/section-9/)强调背景、原因与后果。已实现取舍放在设计说明；迭代只保留当时的问题、交付与证据。
- **随实现交付：** [GitLab文档工作流](https://docs.gitlab.com/development/documentation/workflow/)关联用户可见变更与文档。由本次实现者同步更新，减少Bear事后整理聊天记录的成本。

**增文条件：** 有实质内容和明确读者需求时才增加文档；不预建空目录，不为每个小改动单写报告，不在两处维护任务状态。

**审查责任：** 发布脚本降低同步成本，事实审查与产品取舍仍由本次交付负责。

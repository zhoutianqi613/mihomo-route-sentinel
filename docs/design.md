# 工作原理与业务流程

> [!NOTE]
> **先确认，再复核，最后受约束地切换。** 一次偏慢不等于立即换节点；应急接管也不等于严格合格。

具体字段与命令见 [使用手册](../README.md)。本页数值由当前源码默认配置生成，用户实际配置可以不同。

## 01 三个关键角色

**目标组（Selector）** 是 Sentinel 有权修改的路由选择；**候选组** 提供可选节点；**实际叶子节点** 是最终承担流量的代理。目标组可能选择另一个自动组，因此“组名没变”不代表真实出口没变。

业务路径是：用户的 AI 客户端经 Mihomo 访问上游服务。Sentinel 从旁通过 Controller 探测与选择，检查 HTTPS/TLS、首字节耗时和 WebSocket，并将判断写入状态与日志。它不会读取业务聊天正文。

## 02 恢复流程

**完整业务流程：从发现异常到恢复**

| 步骤 | 系统做什么 | 会产生什么结果 | 什么时候停止或等待 |
|---|---|---|---|
| 1. 读取配置并取得单实例锁 | 校验配置版本、组名、URL、阈值和文件路径 | 得到可信的运行边界 | 未替换占位组名、非法参数或已有实例时明确退出 |
| 2. 检查运行前提 | 执行已启用的客户端、模式和DNS守卫；核对Controller可达性 | 允许继续，或报告修复/阻断原因 | 守卫失败时不继续探测和切换 |
| 3. 识别实际出口 | 解析Selector及叶子，区分外部修改与自身切换 | 明确当前正在验证哪个节点 | 外部选择需要重新准入，不能继承旧健康身份 |
| 4. 探测当前链路 | 多轮检查业务URL，并补充真实连接遥测 | 成功率、平均/最大延迟和异常类型 | 尚未达到确认条件时继续观察 |
| 5. 决定保持还是恢复 | 区分部分失败、延迟退化、尖峰、硬故障及周期择优 | 保持、确认、候选恢复或限流退避 | 最短驻留、改善门槛或切换预算可能抑制普通择优 |
| 6. 取得候选证据 | 优先复用身份匹配且新鲜的快照，缺少时再扫描 | 严格候选、临时候选或无有效候选 | 快照只用于排序；不能代替本次切前可达性证据 |
| 7. 切前复核与选择 | 在有界时间内复核候选，检查守卫与预算，串行修改目标组 | 一次真实的Controller选择及审计记录 | 全部候选不可达或没有相对改善时不盲切 |
| 8. 验证恢复并持续观察 | 常规路径切后验证；应急路径明确降级身份，并在后续周期严格准入 | 严格验证恢复，或待准入/失败隔离 | 失败后按策略尝试后续候选；原节点也要复核，不能盲目回退 |

> [!WARNING]
> **扫描时限不等于恢复时限。** 健康检查与后台快照刷新异步隔离；故障确认、扫描、复核与切换分别计时。不能用“扫描3秒”推导“总故障恢复3秒”。

## 04 典型场景

### 场景一：短暂尖峰后自行恢复

一次偏慢并不立即切换。系统记录异常并按类别继续观察或确认；确认时恢复，则保留当前出口，避免为短暂波动制造新的连接中断。

### 场景二：已确认故障且有新鲜快照

快照提供候选顺序；本次快速复核证明哪个候选当下仍能响应。紧急模式优先相对可用性，允许选择尚未达到严格门槛的更好节点，但必须标记 `emergency-best-effort` 与 `verified=false`，下一周期继续严格准入。

“一秒”是新鲜快照可用、故障已进入恢复路径后的决策与选择目标，不包含最初故障发现、确认等待或冷启动扫描，也不是Windows硬实时保证。

v1.7.1修复了将快速目标当成可用性硬门槛的问题：实际候选可能无法在预留切换时间后的约750ms内响应，却能在更长窗口内返回。快速复核没有相对更优候选时，系统追加一个 `preSwitchValidationDeadlineMs` 窗口（默认3000ms），并行重采一轮全部业务目标；每请求按目标数分配超时，避免首目标占满窗口。新样本单独计算，不用旧快照或短窗口的缺失样本补成成功。恢复成功仍是待严格准入的应急接管，记录 `live-recovery-validation`；总耗时超过一秒时标记未达标，不能以满足SLO为由一直留在故障节点。

### 场景三：多个候选都失败

紧急快速复核只采一轮；最佳候选仍有失败或缺失样本时，也进入扩大的恢复窗口，优先寻找完整可达的候选，减少局部成功导致的无效接管和预算消耗。

结合公共对照URL进行上游故障启发式判断，或在无有效候选时退避。全部候选0%成功时不轮询盲切。对照正常不能证明一定是OpenAI整体故障，也可能存在共享网络因素；需要保留判断依据。

## 05 设计取舍与代码定位

**为什么选择这些设计**

| 决策 | 处理的实际问题 | 选择与代价 |
|---|---|---|
| 按真实AI目标探测 | 通用测速不代表TLS、API或WebSocket可用 | 提高相关性，也带来业务目标依赖和探测负载 |
| 多轮、分级确认 | 单次噪声易导致来回换节点 | 降低误切换，代价是部分异常需要等待确认 |
| 背景快照与切前复核分开 | 故障后全量扫描慢；旧快照又可能失真 | 健康期持续付出探测成本，换取更短恢复路径 |
| 严格准入与应急身份分开 | 所有节点抖动时，坚持严格门槛可能一直留在坏节点 | 接受有标识的短期降级，不能把应急节点写成严格合格 |
| 单进程异步探测、串行控制 | 子进程增加凭据、取消、锁与孤儿进程管理复杂度 | 网络I/O并发，Controller选择串行；仍受主机调度影响 |
| 默认只读，显式启用控制 | 首次配置错误不应立即改路由 | 用户需要先验证配置，再允许修改节点和守卫副作用 |

**模块与证据定位**

| 模块 | 责任 |
|---|---|
| `src/cli.mjs` | 参数、进程锁、生命周期与守卫编排 |
| `src/config.mjs` | 默认策略、配置迁移与边界校验 |
| `src/controller.mjs` | Named Pipe / HTTP Controller通信 |
| `src/watchdog.mjs` | 健康判断、候选快照、预算、恢复与切后处理 |
| `src/link-probe.mjs` | HTTPS CONNECT、TLS、TTFB与WebSocket遥测 |
| `src/guardrails.mjs` | 已启用的客户端、运行模式与DNS守卫 |
| `src/observability.mjs` | 日志轮转、状态快照和可读输出 |

关键配置的约束测试见 `test/config.test.mjs`，候选与恢复见 `test/watchdog.test.mjs`。这些代码/测试入口支持追溯，不代表本页列出的所有真实网络条件都已完成验收。

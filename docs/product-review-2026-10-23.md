# 产品审查：2026-10-23

## 结论

项目已从可用 MVP 收敛为 Windows 可无人值守运行、其他平台安全阻断的 v3 基线。固定全局冷却、错误回滚、可见终端窗口、状态不一致、Dry Run 污染状态、无退避/无切换预算、无上游判断、观测不足、配置不可演进以及外部错误配置旁路均已纳入修复。

## 本轮已修复的 P0 问题

- 当前节点门槛收紧到平均 800 ms、单次 1500 ms；候选准入收紧到平均 600 ms、单次 1200 ms，并要求连续两轮合格。
- 使用分级状态代替单一健康布尔值：部分失败连续 2 周期、纯延迟连续 3 周期、硬故障 5 秒确认。
- 用仅约束纯延迟优化的 120 秒最短驻留替换 10 分钟全局冷却；部分失败和硬故障可立即恢复。
- 延迟型切换要求候选至少改善 200 ms 或 20%。
- 切后验证失败会隔离候选并尝试下一个；只有原节点复测合格才回滚。
- Windows 任务改用隐藏的 Windows Script Host；停止操作会精确清理本项目 Node.js 进程和失效锁。当前普通用户注册 S4U 被系统拒绝，因此未把提权作为运行前提。
- 新增 BAT 服务管理入口。
- 检查循环改用固定起始节拍，避免“探测耗时 + 固定等待”造成周期持续漂移。

## 第二轮已解决

- Dry Run 已改为完全不写正式状态；实际节点、`lastSwitch` 和隔离状态在每条切换/保留路径同步。
- 无合格候选后默认退避 120 秒；滚动 10 分钟最多切换 3 次，硬故障也不可绕过切换预算。
- 新增 Cloudflare 公共对照探测，在多个候选业务目标均失败但对照正常时判定上游故障，并抑制无意义切换。
- 候选扫描并发默认从 12 降至 4；节点样本增加抖动指标。
- 新增 HTTPS CONNECT/TLS/TTFB/总时长与 WebSocket 握手遥测，并写入可轮转的 NDJSON 日志。
- CLI 新增 `--status` 和 `--status-json`，汇总实时选中节点、最近健康、失败计数、隔离、切换预算、最近切换和遥测。
- 日志默认单文件 5 MiB、保留 14 份，并对凭据名字段和 URL 内嵌凭据做脱敏。

## 配置与跨平台产品化

- 引入 `configVersion: 3`；v1/v2 配置可内存迁移，未来版本会明确拒绝，不会被旧程序误解。
- 启动前校验整数、成功率、正则、URL 协议、阈值关系与文件字段，避免运行中才暴露配置错误。
- 示例组名使用 `CHANGE_ME_*` 显式占位，未替换时给出可操作的错误，不再假定所有环境存在 `XFLTD` / `自动选择`。
- 提供 Linux systemd 和 macOS launchd 安装器及统一 `start/stop/restart/enable/disable/status` 管理脚本。

## 第三轮配置守卫

- 每周期检查 Mihomo 运行模式；发现 `direct` 会自动恢复为 `rule` 并通过 Controller 再次读取确认。
- 运行模式使用 Mihomo API 每 5 秒独立检查并复核，不读取或重写可能包含敏感信息的 `config.yaml`。
- DNS 覆写按当前订阅检查；Windows 停止当前会话的唯一 Clash Verge 进程后，只原位修改目标布尔字段，不生成完整配置副本。
- DNS 重载债务跨周期、跨服务重启保留；持久化开关、生成配置、Controller 和运行模式全部复核后才清除。
- 普通 Named Pipe 不再误判为 Clash Verge，Pipe 短暂消失不会永久降级到 HTTP。
- 修复失败、配置目录不可读或重载失败时持续 fail-closed：不探测、不扫描、不切换，并在状态与日志中暴露可执行原因。
- Dry Run 只报告预计修复项，不修改外部应用配置。

## 第四轮选择来源与不可接受尖峰

- Sentinel 以最近已准入的 Selector 与实际叶子节点为基线，区分自身切换与外部手动/程序切换；任一层发生外部变化都会写入明确审计事件。
- 外部选择必须使用真实业务 URL 按候选门槛严格多轮验证；UI 的 `5000 ms` history/占位值不作为准入样本。
- 未通过准入的外部选择会保留待准入状态并立即扫描，不会在下一周期被普通当前节点门槛静默接纳。
- 缺少当前准入策略版本的旧状态会执行一次 `baseline-revalidation`；通过后写入版本，失败则保持待准入并扫描，且不会伪装成新检测到的外部切换。
- 单次真实探测超过公开配置 `policy.immediateMaxSingleMs`（默认 2500 ms）仍属于“不可接受”质量，而非硬故障；它使用独立 `latency-spike` 状态，确认后绕过普通连续退化周期和最短驻留进入扫描。
- 硬故障等级仍严格限定为成功率不超过 50% 或平均延迟超过 3000 ms。
- 所有 Sentinel 实际选择，包括外部节点重新安置、候选尝试、回滚和兜底，仍在 `select` 前执行配置守卫。

## 已知运行边界

- Linux systemd 和 macOS launchd 脚本在 Windows 上通过语法、XML 和关键命令静态检查，但当前无对应 init 系统，目标平台实机权限与生命周期验收仍是发布前检查项。
- 上游故障是多候选业务目标失败 + 公共对照正常的启发式判断，不能替代 OpenAI 官方状态信号。
- 候选组名仍需用户从 Mihomo 实际配置中填写；本版不提供交互式配置向导。

## 第五轮节点择优复盘（2026-10-24）

### 事实与判断

- 印度 01 并非因界面显示值被选中。切换当时原节点已连续退化，50 个候选初筛后只有印度 01 连续两轮达到候选准入线；切后短时抖动时系统尝试日本 04，但日本 04 真实复核只有 75% 成功率，因此回滚印度 01。随后印度 01 多轮真实业务探测约为平均 569–766 ms、成功率 100%。
- Clash Verge 面板的 `999 ms` 是独立时刻、独立目标的历史/测速结果，不等于 Sentinel 的 ChatGPT 与 OpenAI API 业务探测。它是风险提示，但不能单独证明选择错误。
- 本轮只读全候选复测没有发现满足“100% 成功、平均不超过 600 ms、最大不超过 1200 ms且连续两轮合格”的替代节点。因此当前保留印度 01 合理，但它只是“可接受”，不是已证明的全局最优。

### 代码与设计缺陷

- 已修复：切后全部失败时，旧逻辑可能按分数主动选回一个成功率为 0 的失败候选。现在只有每轮仍满足当前健康线的节点才允许临时保活，并强制在下一周期重新严格准入；更差节点只保留当前实际选择，不再额外切换。
- 已修复：单个健康周期会清空连续延迟计数，造成间歇性尖峰长期不触发扫描。现在增加 10 周期滚动窗口，累计 3 次延迟退化即触发评估。
- 已修复：旧逻辑只做故障转移，节点只要勉强健康就永不择优。现在非“优秀”节点每 15 分钟执行一次低频择优，仍受 200 ms 或 20% 改善、最短驻留、隔离和切换预算约束。
- 已修复：初筛只取前 6 名严格复测，单次噪声可能排除真正稳定的第 7 名以后节点。现在每批 6 个、最多复测 18 个，直到取得足够合格候选或达到上限。
- 已修复：嵌套 Selector 切换后复测了组名而非实际叶子节点。现在解析并复测真实叶子，同时记录 Selector 和叶子。
- 已修复：恢复回滚只复测一轮却标记为已验证。现在使用与切后验证相同的轮数，并要求每轮达到当前健康线。
- 已修复：日志只展示合格候选，无法解释低延迟初筛节点为何被淘汰。现在记录每个被拒候选的轮次摘要和失败原因；状态输出增加滚动退化、最近决策、最近候选扫描与临时候选状态。
- 已修复：严格复测阶段未达到候选准入线、但连续各轮都满足当前健康线的节点曾被直接丢弃，导致故障节点在严格候选缺失或切后失败时被继续保留。现在这类节点会进入独立临时候选池：当前节点不健康时先尝试严格候选，全部失败后继续尝试临时候选；周期择优不使用临时候选，临时接管后下一周期仍必须重新严格准入。
- 已修复：历史全候选扫描实测约 123–160 秒，且 `await` 扫描会暂停逻辑健康循环。v6 改为单实例后台扫描，完成后提前唤醒决策；组级 delay API 将约 50 个节点的发现压缩到约 1.2 秒，发现与严格复测共享 3 秒硬截止，过期结果因节点恢复或选择变化而自动作废。
- 已修复：实机发现 3 秒组级并发窗口可能产生“快照合格、切后失败”的假阳性。快速结果现在只建立候选池；正式切换前必须再通过单节点串行多轮门禁。门禁失败不修改路由、不消耗切换预算，避免连续试错导致 Codex WebSocket 重连。

### 产品结论

可用性优先仍是正确主目标，但“健康”不等于“最优”。周期择优解决长期停留在可接受但偏慢节点的问题；严格准入、显著改善、最短驻留与切换预算共同限制抖动。界面单点测速仍只作为人工告警线索，自动决策继续以真实业务链路的重复样本为准。

### 实机验收结果

- 新版首次周期择优从印度 01 发现并尝试日本 01。日本 01 首次切后复核未达到严格候选线，因此先进入待准入状态；下一周期严格准入达到 100% 成功、平均 407 ms、最大 455 ms，最终从“可接受”改善到“优秀”。
- 随后真实发生 HTTPS/WebSocket 同时失败与业务探测硬故障。系统完成 5 秒确认、隔离内扫描、一次全候选隔离旁路、候选切后复核失败和原节点安全回滚，没有把失败候选标记为成功。
- 故障后日本 01 恢复到 100% 成功、平均 487 ms、最大 754 ms；HTTPS 与 WebSocket 真实链路均恢复。最终服务为 Windows 隐藏后台单实例，`stop/start/restart` 生命周期均通过。

## 验收重点

- 2500 ms 以内的单次普通尖峰不切换；超过 2500 ms 的不可接受尖峰进入 5 秒确认，确认恢复不切换，确认仍超线才立即扫描。部分失败连续 2 周期才切换；纯延迟连续 3 周期且改善显著才切换。
- 当前节点只有在 100% 成功、平均不超过 800 ms、最大不超过 1500 ms 时才视为健康；1000/2500 ms 只属于退化或最低可用警戒区间。
- 候选只有在 100% 成功、平均不超过 600 ms、最大不超过 1200 ms，并连续两轮验证合格时才准入。
- 硬故障即使发生在最近一次切换后的 120 秒内，也能完成确认和故障转移。
- 候选失败后尝试下一候选，不直接回到未经复测的旧节点。
- Windows 启动和重启不显示常驻终端窗口；停止后不存在本项目残留进程。

## 第六轮：候选快照与一秒紧急降级（2026-10-25）

### 一句话产品结论

在故障窗口重新全局扫描并串行验证候选不符合可用性优先目标；健康期预热候选快照、故障时限时复核并选择相对最优节点是合理方向，但一秒承诺必须限定为“新鲜快照可用后的决策与切换 SLO”，不能包含首次故障探测和冷启动扫描。

### 分级问题与决策

| 优先级 | 类型 | 证据与用户影响 | 决策 |
|---|---|---|---|
| P0 | 已核实事实 | 2026-10-25 实机中 4 个候选的扫描只需 2532 ms，但原串行切前门禁累计约 39 秒；当前节点持续 `Error` 时恢复窗口过长。 | 候选切前复测改为统一截止内并行，默认总截止 3000 ms。 |
| P0 | 已核实事实 | 故障发生后才启动全局扫描，至少增加约 2.5 秒，无法满足一秒恢复目标。 | 持续运行期间每 30 秒后台刷新候选快照；60 秒内且 Selector/叶子匹配的快照可直接用于恢复，预算暂时耗尽也不停止只读预热。 |
| P0 | 产品决策 | 严格要求 100% 成功会在全节点抖动时导致“保持已知故障节点”。 | 紧急模式允许选择非 100% 节点，按成功率降序、平均/最大延迟升序；必须至少成功一次并优于当前节点。 |
| P0 | 风险边界 | 若所有节点都是 0%，所谓“最高成功率”仍为 0%，切换只会制造断线和切换风暴。 | 全部 0% 或没有相对改善时不切换；切换预算、隔离和配置守卫不得绕过。 |
| P1 | 合理推断 | 串行逐节点验证理论上更节制，但任一节点超时都可能耗尽一秒预算。 | 缓存排名决定逻辑优先级，前列候选在约 750 ms 窗口内并行快速复核，剩余预算用于守卫与 Controller 选择；快照不替代本次可达性证据。 |
| P1 | 可观测性 | 允许非严格节点接管后，如果仍显示为“已验证”，会误导运维判断。 | 状态标记 `emergency-best-effort`、`verified=false`，记录 `decisionDurationMs`/`deadlineMet`，下一周期强制严格准入。 |
| P2 | 未知信息 | Windows 普通调度和 Mihomo Controller 不提供硬实时保证，极端 CPU/IO 阻塞仍可能超过 1000 ms。 | 一秒作为可测 SLO 而非数学硬保证；超时照常记录并进入后续恢复，不伪造达标。 |

### 推荐默认策略

- 候选快照刷新：30 秒；最大年龄：60 秒。
- 常规候选并行门禁：最多 3000 ms。
- 紧急决策与切换：最多 1000 ms，其中约 250 ms 预留给配置守卫、Controller `select` 和叶子确认。
- 排序：成功率优先，其次平均延迟、最大延迟、抖动和稳定名称排序。
- 快速复核只使用本次成功样本；整个窗口无结果时保持当前路由并记录不可用，不能仅凭历史快照盲切。
- 同成功率候选只有达到既有 200 ms 或 20% 改善之一才替换当前节点。
- 紧急节点只负责恢复相对可用性，不获得严格准入身份；下一周期重新按 100% / 600 ms / 1200 ms / 两轮门槛验证。

### 验收标准

1. 4 个候选、每个 2 轮 × 2 URL 的模拟切前复测必须并行完成，不随候选数线性累加。
2. 新鲜快照存在时，故障路径不得产生第二次 `candidate-scan-started`。
3. 没有 100% 候选时选择成功率最高节点；同成功率按延迟排序。
4. 全部候选 0% 或本次快速复核全部超时时不得调用 Controller `select`。
5. 模拟紧急决策到切换小于 1000 ms，并在日志中留下实际耗时和是否达标。
6. 缓存过期、选择不匹配、切换预算耗尽或配置守卫失败时保持安全阻断。

### 分阶段路线图

- 本轮：候选快照、并行门禁、相对最高成功率紧急接管、配置/日志/状态说明及自动化测试。
- 后续 P1：积累实机 SLO 分位数，分别统计探测确认、快照命中、复核和 Controller 切换耗时。
- 暂不实现：操作系统硬实时调度、跨设备共享候选快照、用未经验证的 0% 节点轮询碰运气。
